## 4. Talent profiles, applications, identity claims

Two distinct flows (PRD §6.3, data model): **Application** = "I'm a new Rising Star, give me a talent account" (no existing profile). **Identity claim** = "this pre-seeded unclaimed Talent profile is me". Approval of either grants the `talent` role and links `Talent.userId`.

#### TAL-01 `POST /api/talent-applications` — CONFIRMED (decision 14)

Status: :badge[implemented]{color="success"}
- **Proof:** `tests/e2e/talent.test.ts`
- **Purpose:** "Building my fandom" → apply to be a Rising Star.
- **Caller:** Signed-in user without `talent` role.
- **Body:** `{ categoryId, displayName, bio (≤1000), links: {label,url}[≤5] (https only), imageMediaId?, evidenceMediaIds?: string[] }`.
- **201:** `TalentApplication { id, status: "pending", categoryId, displayName, bio, links, imageUrl, submittedAt, decidedAt: null, decisionReason: null }` (applicant sees their own evidence filenames only, never other applicants').
- **Errors:** `VALIDATION_FAILED` (inactive category, non-https link, media not owned by caller); `CONFLICT` (open `pending` application exists → `existingId`); `FORBIDDEN` (already talent); `UNAUTHENTICATED`.
- **Side effects:** creates `TalentApplication`; counted on the admin dashboard (no admin notification). If the user's latest application was declined < 7 days ago → `INVALID_STATE { details.reapplyAfter }`. Only one `pending` application per user → `CONFLICT`.
- **Tests:** second pending application → 409 with existingId; talent user → 403; media IDs belonging to someone else → 400.

## 12. Admin, moderation, audit

All `/api/admin/**` routes: `requireRole('admin')` in a Nitro route-level middleware **and** re-checked in each handler (defence in depth). Every state-changing admin route writes an `AdminAudit` row in the same transaction as the change (acceptance #11). Launch scope = the 7-item admin set (decision 11).
