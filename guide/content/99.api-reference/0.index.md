## 1. API conventions (all PROPOSED)

### 1.1 Base path, format, versioning
- Base path `/api`, served by Nitro file routes (`server/api/**`). No `/v1` prefix (decision 20.4); contracts evolve additively (new optional fields, new endpoints). A breaking change requires a new path and a deprecation note.
- JSON only, `camelCase` keys, `Content-Type: application/json`. Request bodies capped at **64 KB** (uploads go direct to object storage — MED-01, §13).
- IDs: UUID (v7 so they are time-sortable) as strings. Timestamps: ISO 8601 UTC (`2026-10-31T12:00:00.000Z`); clients localise.
- **Single resources** are returned bare (`{ "id": ..., ... }`). **Lists** always use the pagination envelope (§1.3). No `data` wrapper.
- Enum values are lowercase snake_case strings (`pending`, `originals_only`).
- Unknown body fields are rejected (`VALIDATION_FAILED`) so typos never silently no-op.
- Validation with **Zod** (decision 20.3) via h3's `readValidatedBody` / `getValidatedQuery`. Data access with **Drizzle** + versioned migrations (decision 20.2).

### 1.2 Error envelope
One shape for every non-2xx response:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Some fields are invalid.",
    "requestId": "req_01JBX6Q2Z4...",
    "details": { "fields": { "username": "must be 3-30 characters" } }
  }
}
```

`message` is human-safe (never stack traces, SQL, provider errors). `details` is optional and code-specific.

| code | HTTP | When | `details` |
|---|---|---|---|
| `VALIDATION_FAILED` | 400 | Bad path/query/body, unknown fields, bad cursor | `fields: {path: reason}` |
| `UNAUTHENTICATED` | 401 | No/expired session | — |
| `FORBIDDEN` | 403 | Signed in but not allowed (role/ownership/membership) | `reason?` (e.g. `not_member`) |
| `ACCOUNT_SUSPENDED` | 403 | Caller's account is suspended | — |
| `NOT_FOUND` | 404 | Missing **or** caller may not know it exists (see rule below) | — |
| `CONFLICT` | 409 | Uniqueness clash (username taken, open application exists) | `existingId?` |
| `INVALID_STATE` | 409 | State transition not allowed (approve an already-rejected mission) | `currentStatus`, `allowed[]` |
| `EMAIL_NOT_VERIFIED` | 403 | Signed in but email not yet verified (decision 1c: required before using the app) | — |
| `ONBOARDING_REQUIRED` | 403 | Fan action (join, react, reply, complete mission) before onboarding is complete | — |
| `FEATURE_DISABLED` | 403 | Route exists but feature is switched off pending a decision | `feature` |
| `PAYLOAD_TOO_LARGE` | 413 | Body > limit | `limitBytes` |
| `RATE_LIMITED` | 429 | Too many requests (`Retry-After` header set) | `retryAfterSeconds` |
| `INTERNAL` | 500 | Anything unexpected; logged with `requestId` | — |

**Existence-hiding rule:** if the caller may not see a resource at all (another user's application, an unpublished drop, a pending mission they don't own), return `NOT_FOUND`, not `FORBIDDEN`. `FORBIDDEN` is for resources the caller can see but cannot act on (e.g. a visible community's member-only content, or a talent editing someone else's drop they can see).

### 1.3 Pagination envelope
```json
{ "items": [ ... ], "nextCursor": "eyJrIjpb...fQ.sig" }
```
- `nextCursor: null` means no more pages. Optional query: `limit` (default 20, max 50), `cursor`.
- Cursor = base64url(JSON `{ v:1, k:[sortKey..., id], f:<hash of filters> }`) + `.` + HMAC-SHA256 (server-only secret `CURSOR_SECRET`). Opaque to clients.
- Keyset pagination only (`WHERE (sort_key, id) < ($1, $2)`), never `OFFSET`, so pages are stable and non-duplicating under inserts (PRD acceptance #7).
- A cursor reused with different filters, tampered with, or from another endpoint → `VALIDATION_FAILED` `details.fields.cursor = "invalid"`.
- Every list states its sort keys; `id` is always the final tie-breaker.
- No total counts on lists (expensive and unstable); counts appear only where a route explicitly lists them (e.g. `memberCount`).

### 1.4 Request tracing
- Nitro middleware assigns `requestId` (`req_` + ULID) per request, returns it as the `X-Request-Id` response header on **every** response and in every error body.
- Inbound `X-Request-Id` is ignored (prevents log spoofing); Vercel's `x-vercel-id` is logged alongside for correlation.
- Structured JSON log line per request: `requestId, method, route pattern, status, durationMs, userId?` — no bodies, emails, tokens or evidence URLs.

### 1.5 Authentication, roles and authorization
- Session via **HTTP-only, Secure, SameSite=Lax cookie** issued by **Better Auth**, with users and sessions stored in Neon (decision 1). State-changing routes require `Content-Type: application/json` and an `Origin` check (CSRF defence for cookie auth).
- A single server helper `requireUser(event)` → `401` / `ACCOUNT_SUSPENDED` / `EMAIL_NOT_VERIFIED` (only `GET /api/me`, auth routes and public catalog reads skip the verified check); `requireRole(event, 'admin')`; `requireCommunityRole(event, communityId, 'owner'|'member')`.
- Roles on the user record: `fan` (default), `talent` (granted when an application is accepted or a claim verified), `admin` (Super Admin; seeded, never self-assignable). Originals is a **membership attribute**, not a role (PRD §4).
- Community authority: **one talent owns one community** (`ownerTalentId`, unique) — decision 8. "Owner" = the user linked to that talent. Admin can do anything an owner can. No co-managers at launch.

### 1.6 Idempotency policy (per-endpoint choice shown in each route)
| Action type | Behaviour on repeat |
|---|---|
| Join community | `200` with the **existing** membership (first call `201`). Never a second row; never a second Originals slot. |
| Leave community | `200` with the membership in `left` state; repeated leave returns same. |
| React to a drop | `PUT` (set my reaction) — naturally idempotent. |
| Submit mission completion (non-repeatable mission) | `200` with the **existing** completion (first call `201`). No second XP grant. |
| XP grants | Never client-callable. Internal `grantXp()` writes a ledger row with a unique key `(userId, sourceType, sourceId)`; a duplicate insert is a no-op inside the same transaction. |
| Admin/owner decisions (accept, approve, verify, veto) | Repeating the **same** decision → `200` with current resource (no new audit row). A **different** decision on a decided record → `409 INVALID_STATE`. |
| Create talent application / identity claim while one is open | `409 CONFLICT` with `details.existingId`. |
| Create drop / reply / mission / watch party | Optional `Idempotency-Key` header (UUID). Same key + same caller within 24 h → original `201` response replayed. Without the header, each call creates a record. |

### 1.7 Rate limits (PROPOSED defaults; stored in a Postgres table — decision 20.6)
- Auth routes: 10/min/IP. Username check: 30/min/IP. Writes (drops, replies, reactions, reports): 60/min/user. Admin: none beyond auth.
