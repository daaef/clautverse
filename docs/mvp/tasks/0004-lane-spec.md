## 3. Lane set enforcement: schema vs. app-level validation

**Decision: enforce the canonical six-value set in application code (zod `z.enum`), not as a
Postgres `CHECK` constraint or a native enum type, for Stage 1.**

Reasoning, stated so it can be checked:

- `membership.lane` is declared as free text today (`app.ts:95`) specifically because, per the
  column comment and DEC-01's own text, lane values were undefined; DEC-01 resolves the *name
  list* but explicitly leaves open whether lanes can ever change (`decisions.md:44-45`, "Still
  open... whether lanes can be changed after selection"). A later PRD revision or a second-lane
  rule change (TASK-0010, Stage 2) could alter the canonical set again.
- A Postgres `CHECK` or native `enum` type requires a schema migration to add, remove, or rename
  a value. An application-level `z.enum([...])` list requires only a code change and is reviewed
  and tested the same way as any other route contract change.
- Trade-off being accepted: a `CHECK` constraint is the stronger guarantee — it protects against
  any future code path (a script, a different route, a direct DB write) inserting an invalid
  value, whereas app-level validation only guards requests that go through this route. Given the
  column is already free text and no other route writes it (confirmed: `0001-findings.md:23`,
  "grep for `.lane`/`lane:` across `server/` finds only reads"), this risk is judged acceptable
  for Stage 1. **If a second write path to `membership.lane` is ever added (e.g. an admin
  lane-override route), this decision must be revisited** — a `CHECK` constraint would then catch
  what app-level validation on this route alone cannot.
- This is a specification-level recommendation, not an owner ruling already on record. If the
  owner wants a DB-level constraint instead, say so before implementation; it changes the
  migration (adds a `CHECK` or converts the column to a native enum) but does not change any of
  the route behaviour described below.

**Canonical value list and proposed storage form:**

PRD §6.8 names the six lanes with capitalized, space-containing display names: Rider, Fandom
Builder, Builder, Analyst, Creator, Mutual (`Clautverse Ecosystem PRD.md:430-464`). Every other
free-text-turned-enum column in this schema stores lower\_snake\_case machine values distinct from
their display label (e.g. `mission.proof: 'none'|'link'|'text'`, `notification.type` values like
`watch_party.created`, `xpTransaction.sourceType: 'mission_completion'|'admin_adjustment'` — all
read in `app.ts`/`utils/missions.ts` above). **No PRD line or schema comment specifies a storage
slug for lane values — this is not an owner decision on record and must not be invented as final.**
Proposed, for owner/reviewer confirmation before implementation:

| Display name (PRD §6.8, canonical) | Proposed stored value |
|---|---|
| Rider | `rider` |
| Fandom Builder | `fandom_builder` |
| Builder | `builder` |
| Analyst | `analyst` |
| Creator | `creator` |
| Mutual | `mutual` |

If the owner prefers storing the exact display string (`"Fandom Builder"`) instead of a slug,
every validation rule, test, and response shape below still applies — only the literal set
member strings change. **This table is a proposal, not a decision already made; flag to the
owner/reviewer before the implementer encodes it.**

## 4. Join request contract

### 4.1 Request body

`POST /api/communities/:id/join`

```json
{ "lane": "rider", "alertsEnabled": true }
```

- `lane`: **required**, `z.enum(['rider', 'fandom_builder', 'builder', 'analyst', 'creator',
  'mutual'])` (pending §3's confirmation of the exact string set). No default. Must not be
  silently coerced from an absent/empty/invalid value (task brief acceptance criterion 4,
  `0004-fandom-browse-join-one-lane.md:50-51`).
- `alertsEnabled`: unchanged, optional boolean, same as today (`join.post.ts:6`).
- The body schema stays `.strict()` (matching the existing convention at `join.post.ts:6`, and
  every other body schema read in `server/api/**` above) — an unknown extra key is a validation
  failure, not silently ignored.

### 4.2 Validation error cases and exact responses

All of these use the project's standard shape: HTTP 400, `code: 'VALIDATION_FAILED'`
(`server/utils/api-error.ts:4`), with a `fields` object naming the offending field.

| Case | Request `lane` value | Response |
|---|---|---|
| Missing | key absent from body | `400 VALIDATION_FAILED`, message `"Some fields are invalid."`, `fields: { lane: 'invalid_type' }` — this is the literal message/shape `parseOrThrow` produces for any failed zod parse (`validate.ts:13-17`); the exact per-field string depends on the zod version's default issue code, which this session did not re-verify against the installed zod version — **NOT VERIFIED: confirm the exact zod v4 issue-code string `toFields` will emit for a missing required enum key before asserting the literal `fields` value in a test; assert on `fields.lane` being present and non-empty if the literal string cannot be confirmed.** |
| Empty string | `""` | Same `VALIDATION_FAILED` shape — `""` is not a member of the enum, so `z.enum` rejects it the same way as any other non-member string. |
| Not in the approved set (e.g. `"vip"`) | any string outside the 6-value set | Same `VALIDATION_FAILED` shape. |
| Sent as an array (e.g. `["rider", "mutual"]`) | array | Same `VALIDATION_FAILED` shape — `z.enum` only accepts a string, so an array fails type validation before set-membership is even checked. This is the mechanism that satisfies task brief acceptance criterion 2 ("duplicate lane assignment... impossible... even if the field is accidentally sent as an array") for the join request itself — the array case is rejected outright, never partially accepted. |

No new error code is introduced; this reuses `VALIDATION_FAILED`, already defined at
`server/utils/api-error.ts:4` with HTTP status 400.

### 4.3 Unaffected existing behaviour

- Joining a vetoed or nonexistent community still returns `404 NOT_FOUND` before the lane is
  even considered — `loadVisibleCommunity` (`community.ts:46`) runs first in the handler (line
  16, before the body is read at line 12... **note:** in the current code the body is read at
  line 12, *before* `loadVisibleCommunity` is called at line 16. The implementer must decide
  whether lane validation should run before or after the community-existence check. Recommended:
  validate the body first (fail fast on a malformed request regardless of which community was
  named), matching the current line order where `readJsonBody` already runs first. This does not
  change the NOT_FOUND-before-FORBIDDEN existence-hiding rule, since lane validation and
  community-existence are independent checks on different inputs.
- Rate limiting (`rateLimit(event, 'community-join', u.id, 60, 3600)`, line 11) is unchanged —
  3 join attempts per hour per user, regardless of lane value or outcome.
- `requireUser(event, { onboarded: true })` (line 9) — join remains restricted to onboarded
  users; this spec does not change that gate.

## 5. Idempotent rejoin semantics (active / left / removed branches)

### 5.1 What the PRD says

- PRD §6.8 line 486: "Leaving a fandom **permanently removes** the fandom-specific lane
  assignments along with that fandom's XP and badge progress."
- PRD §6.8 line 487: "Rejoining after a permitted rejoin **begins a new fandom membership**
  under the platform's applicable rules."

### 5.2 What the code does today (confirmed, not this task's to change)

Leave (`leave.post.ts:15`) does **not** clear `lane` — it only sets `status: 'left'` and
`leftAt`. This is a confirmed gap against PRD line 486, already logged as absent in
`evidence-matrix.md` row 24 ("Atomic XP/tier cleanup on leave/removal (TASK-0012-B)... none
found") and explicitly assigned to **TASK-0012-B**, not this task, in `decisions.md` DEC-04's
"Blocks cleared for" note (`decisions.md:118-121`: "the leave-cleanup side of this ruling is
implemented in TASK-0012-B"). **This spec does not change `leave.post.ts`.**

### 5.3 The resulting question this task cannot avoid

Because `leave.post.ts` currently leaves the old `lane` value sitting on the row, and
`join.post.ts`'s reactivation branch (lines 20-24) currently does not touch `lane` at all, adding
a *required* `lane` field to the join request creates an ambiguity the task brief does not
resolve on its own: **on rejoin (existing row with `status: 'left'`), is the submitted `lane`
value written, ignored, or is lane omission allowed because a value already exists on the row?**

**This is not settled by any PRD line, DEC row, or existing code read in this session. It is
flagged here rather than decided silently, per this role's no-silent-workaround rule.**

**Recommendation (for owner/reviewer confirmation before implementation):** require and write
`lane` on **every** call to this route that results in an active membership — both the
first-join `insert` branch and the `left`-row reactivation branch — unconditionally overwriting
whatever `lane` value (if any) is already on the row. Reasoning:

1. It makes the join contract uniform: the request body requirement ("lane is required") does
   not need a conditional branch based on membership history, which the client cannot easily
   know in advance of calling the route.
2. It is consistent with PRD line 487 ("begins a new fandom membership... under the platform's
   applicable rules") — treating rejoin as a fresh lane choice rather than resurrecting a stale
   one.
3. It matches the existing precedent in the same function: `alertsEnabled` is already
   unconditionally overwritten on the reactivation branch when supplied (`join.post.ts:21`) — the
   reactivation path already treats some join-time inputs as fresh, not preserved.
4. It makes this task's behaviour correct regardless of whether TASK-0012-B's leave-side lane
   clearing has shipped yet — since every join call rewrites `lane`, it does not matter whether
   the old value was cleared on leave or left stale; the row always reflects the just-submitted
   choice.

**Alternative rejected (stated so the owner can override):** preserving the old lane value and
making `lane` optional on rejoin was considered and rejected, because task brief acceptance
criterion 1 requires lane to be required "once lane becomes a required, enumerated field" without
carving out a rejoin exception, and because preserving a lane chosen under a possibly-different
canonical set (if DEC-01's "still open" question about changing lanes after selection is ever
resolved differently) would silently resurrect a value the fan no longer affirmed.

**`removed` branch:** unchanged. `join.post.ts:19` already throws `FORBIDDEN` with `reason:
'removed'` before any lane logic would run; this task does not alter that line. Whether that
block is permanent or time-limited is DEC-03's open question (`decisions.md:72-84`), not this
task's.

### 5.4 Updated branch table for `join.post.ts`

| Existing row state | Lane required in request? | Effect on `lane` column |
|---|---|---|
| none (first join) | Yes | Insert with submitted `lane` value |
| `active` | N/A — request is rejected before reaching lane logic? **See §5.5.** |
| `left` | Yes (per §5.3 recommendation) | Overwrite with submitted `lane` value on reactivation |
| `removed` | N/A | `FORBIDDEN reason: 'removed'`, unchanged from today |

### 5.5 The `active` branch — a second gap this spec surfaces

Today, calling join while already `active` (`join.post.ts:18`) returns the existing row
unchanged with no validation of the request body against the current state at all — the
handler returns before even looking at `alertsEnabled` in that branch. Once `lane` becomes
required in the request schema, **the request body is still parsed by `readJsonBody` at line 12,
before any of these branches run** — so a join call while already active will still require a
syntactically valid `lane` in the body (zod validation happens before the database read), but
**that value is discarded**: the existing active row is returned unchanged, with whatever lane
it already has. This is a pre-existing pattern (the same already happens to `alertsEnabled`
today — a resend while active does not update it either) and this spec does not propose changing
it, since the task brief's idempotency requirement (brief line 51-52, "join retried with the same
Idempotency-Key → original response replayed, not a second lane assignment") only speaks to the
idempotency-key path (§6 below), not to a bare resend of `POST join` without a key while already
active. **Flag to the owner: is "already active, resend join with a different lane" expected to
be a no-op (current proposed behaviour) or should it be rejected as `INVALID_STATE`? Not decided
by any source read this session — recommend no-op (matches existing `alertsEnabled` precedent)
unless the owner says otherwise.**

## 7. Defect #5 fix — `ON CONFLICT` on the membership insert

**Confirmed defect**, cited at `evidence-matrix.md:224-229` and `0001-findings.md:70`: the
membership insert at `join.post.ts:28` is a plain `tx.insert(m).values({...}).returning()` with
no `.onConflictDoNothing()`. The unique constraint `membership_user_community_uq` on
`(userId, communityId)` (`app.ts:100`) exists, so a race that reached this insert twice for the
same `(userId, communityId)` pair would surface Postgres error code 23505 as an unhandled
exception rather than a graceful response. Today this is "latent" per the evidence matrix because
the row lock on the community (line 16) and the row lock on any existing membership (line 17)
should serialize concurrent calls from the same user — but the project's own documentation
(`guide/content/99.api-reference/3.communities.md:40`, a documentation claim, not verified route
code) describes a different mechanism (`INSERT ... ON CONFLICT DO NOTHING`) that this task's test
expectations cite as the expected concurrency guarantee (brief line 58-59).

**Fix required by this task:** change the insert at `join.post.ts:28` to use
`.onConflictDoNothing()` (the same pattern already used elsewhere in this codebase for
first-write-wins races — e.g. `server/utils/missions.ts:18`, `server/api/watch-parties/[id]/rsvp.put.ts:13`,
`server/api/talents/[id]/claims.post.ts:23-24`, `server/api/talent-applications/index.post.ts:31`)
and handle the "no row returned" case by re-reading the existing row and returning it gracefully
instead of propagating a 500. Concretely:

```
const [row] = await tx.insert(m).values({ userId: u.id, communityId: id, alertsEnabled: alertsEnabled ?? true, lane, originalPosition: position })
  .onConflictDoNothing().returning()
if (!row) {
  const [existingRow] = await tx.select().from(m).where(and(eq(m.userId, u.id), eq(m.communityId, id))).limit(1)
  return { created: false, row: existingRow! }
}
return { created: true, row }
```

This is a structural illustration of the required behaviour, not a prescribed final code
structure (per this role's remit, this spec states what must be true, not exact code). What must
be true:

1. A race that reaches the insert twice for the same `(userId, communityId)` must never surface
   a raw 500 / unhandled 23505 to the client.
2. The losing request of the race must receive a graceful response (200, with the winning row's
   data) rather than an error, consistent with the "retried join → original response replayed"
   expectation in the brief.
3. The `originalsAssigned` counter increment at line 27 happens **before** the insert in the
   current code, inside the same transaction. If the insert is discarded by `ON CONFLICT DO
   NOTHING`, the counter increment from this attempt must not double-count — because the
   community row is lock-protected (line 16) for the whole transaction, only one concurrent
   transaction can reach the counter increment and insert at all under the current locking
   scheme; the `ON CONFLICT` branch is a defence for an edge case the locks are not expected to
   let happen, not the primary concurrency mechanism. **This ordering must be preserved or
   explicitly re-reasoned by the implementer if changed** — do not reorder the counter increment
   relative to the lock acquisition without re-verifying the 100-cap guarantee in
   `evidence-matrix.md §6`.

## 10. Acceptance criteria (restated as testable rules)

1. `POST /api/communities/:id/join` with no `lane` key in the body → `400 VALIDATION_FAILED`,
   `fields.lane` present. (task brief AC1)
2. Same request with `lane: ""` → `400 VALIDATION_FAILED`. (brief AC4, empty string case)
3. Same request with `lane: "not_a_real_lane"` → `400 VALIDATION_FAILED`, lane is **not** written
   to any row (no partial commit). (brief AC4)
4. Same request with `lane: ["rider", "mutual"]` (array) → `400 VALIDATION_FAILED`, never
   interpreted as "both lanes" or "first element wins". (brief AC2)
5. Valid single join (`lane: "rider"`, no prior membership row) → `201`, membership row created
   with `lane: 'rider'`, `membershipView` response includes `lane: 'rider'`. (brief "valid single
   join")
6. Two concurrent `POST join` calls from the same user for the same community (same or different
   valid `lane` values) → exactly one membership row results; the losing request gets a graceful
   `200`/`201` response reflecting the winning row's actual stored lane, never a raw 500.
   (brief "concurrent joins," defect #5 fix, §7 above)
7. Join while an existing `active` membership row exists → `200`, existing row unchanged,
   **current `lane` on the row is returned, regardless of what `lane` was sent in this request**
   (§5.5 — flagged to the owner as a judgement call, default no-op recommended).
8. Join after `leave` (existing `left` row) with a valid `lane` in the body → `200`, row
   reactivated (`status: 'active'`, `leftAt: null`), `lane` **overwritten** to the newly submitted
   value (§5.3 recommendation — flagged to the owner for confirmation before implementation).
9. Join after `leave` with `lane` **missing** from the body → `400 VALIDATION_FAILED` (same as
   the first-join case; lane is required on every call per §5.3's uniform-contract
   recommendation, pending owner confirmation).
10. Join against a `removed` membership row → `403 FORBIDDEN`, `reason: 'removed'`, unchanged
    from today — lane is never considered. (existing behaviour, `join.post.ts:19`)
11. Join against a vetoed or nonexistent community → `404 NOT_FOUND`, existence-hiding rule
    preserved regardless of the `lane` value sent (per `guide/content/99.api-reference/0.index.md:164`,
    a documentation claim describing the existence-hiding convention, consistent with the code
    behaviour at `community.ts:46` which this session did read directly).
12. `GET /api/communities/:id/members` response rows already include `lane` per row
    (`members.get.ts:26`, confirmed, no change required) — a test should confirm this stays true
    once lane is actually populated by real joins (today it is always `null` because nothing
    writes it).
13. `GET` on a membership / join response never includes a value outside the six-member set
    (enforced at write time by §3's validation, not by any read-time filtering — there is no
    read-time filtering of `lane` anywhere in the code read this session).

## 11. Test expectations (for test-author)

Per the task brief (`0004-fandom-browse-join-one-lane.md:56-61`):

- Valid single join with each of the six lane values (at least one explicit test per value, plus
  one that is not exhaustively repeated for brevity — minimum: one happy-path test per lane

- Missing lane → `VALIDATION_FAILED`.
- Invalid lane string → `VALIDATION_FAILED`.
- Lane sent as an array → `VALIDATION_FAILED` (not partially accepted).
- Duplicate join while `active` → idempotent 200, existing lane unchanged (§5.5).
- Rejoin after `left` → lane required, overwritten (§5.3) — **test-author should write this as

  owner before these tests are finalized.**
- Join after `removed` → `FORBIDDEN`, unchanged (regression test, not new behaviour).
- Concurrent joins (two simultaneous requests from the same user/community pair) → exactly one
  membership row in the database afterward, and **neither response is a 500** (defect #5
  regression test — this is the one test in this set that exercises §7's fix directly; it should
  attempt to trigger the race at a point where the row lock's sequencing could plausibly be
  defeated, e.g. by exercising the `ON CONFLICT` path directly if the test harness can bypass the

  true race cannot be reliably reproduced in a test).
