    Part 2 · Foundations

    Checking input, paging and rate limits

    About 5 min read

    Three helpers that almost every endpoint uses: one that checks incoming data, one that splits long lists into pages, and one that limits how often someone can call. We also write our first automated test.

    Checking incoming data with Zod#

    In plain words

    Never trust what arrives from outside. A request might have a missing field, a number where text should be, or something hostile. So each endpoint first describes the shape it expects, and anything that does not fit is rejected with a clear message before it can touch the database.

    Zod lets us describe that shape in code. A tiny example, which is not part of the project:

    This says: the body must be an object with a lane that is one of two words, optionally an alertsEnabled true/false, and nothing else (.strict() rejects unknown fields; most real endpoints use it, so a typo in a field name is an error rather than silently ignored).

    Create server/utils/validate.ts, the helpers every endpoint uses to apply such a shape:

    • toFields turns Zod's list of problems into { "lane": "Invalid option…" }, which is what the error's details.fields shows. Array positions are written like links[0].url.
    • readJsonBody(event, schema) reads the request body, refuses invalid JSON, then validates it. readQuery does the same for ?a=1&b=2 parts of the address.
    • readIdParam(event) reads [id] from the path and insists it is a UUID. A malformed ID is answered with NOT_FOUND (not a validation error), so a made-up ID looks the same as an ID that simply does not exist.
    • readUserIdParam exists because user IDs from Better Auth are opaque text, not UUIDs.

    In programming terms

    Every failure is thrown as apiError('VALIDATION_FAILED', …) from chapter 6, so a bad request automatically gets the standard error shape. z.infer<T> gives you the TypeScript type of validated data, so after readJsonBody returns you are working with correctly typed values.

    Long lists: pages and cursors#

    In plain words

    A list of 50,000 communities cannot be sent in one go. We send a page (say 20), plus a bookmark ("cursor") saying where the next page starts. The caller sends the bookmark back to get the next page.

    In programming terms

    The classic way is page=2 (offset pagination), but it breaks when rows are added while someone is scrolling: items shift and you see duplicates or skip some. We use keyset pagination: the bookmark records the last item's sort values (such as its timestamp and ID), and the next query says "give me rows after this one". That stays stable and is fast with an index.

    The bookmark must be tamper-proof; otherwise someone could invent one. So it is signed. Create server/utils/cursor.ts:

    • The cursor is base64url(json) + "." + base64url(signature). The signature is an HMAC (a fingerprint made with a secret, here cursorSecret from chapter 2).
    • When decoding, we recompute the fingerprint and compare with timingSafeEqual, which takes the same time whether or not the first bytes match. That prevents guessing a signature by timing. A forged or garbled cursor decodes to null.

    Now the helper that endpoints use. Create server/utils/paginate.ts:

    • pageQuery is the shared ?limit=&cursor= shape: limit from 1 to 100 (default 20). z.coerce.number() turns the text "20" from the address into a number.
    • readCursor(cursor, scope) verifies the signature and that the cursor was made for the same scope. The scope is a label such as com-popular; it stops a cursor from the "popular" list being reused on the "newest" list.
    • toPage(rows, limit, …) expects you to ask the database for limit + 1 rows. If you got more than limit, there is a next page, and the last kept row becomes the new cursor. Fetching one extra row avoids a separate "is there more?" query.
    • The result is always { items, nextCursor }; nextCursor is null on the last page.

    Rate limiting#

    In plain words

    Without limits, one person (or a script) could hammer the server or try thousands of passwords. A rate limit says "at most N calls per minute".

    Create server/utils/rate-limit.ts:

    • Usage reads like await rateLimit(event, 'drop', user.id, 30, 60): "at most 30 drop calls per user per 60 seconds".
    • It uses the api_rate_limit table from chapter 4. One SQL statement either inserts the first hit, resets an expired window, or adds one to the count, and returns the new count. Doing it in one statement makes it safe when many requests arrive at the same instant.
    • When the limit is passed it sets a Retry-After header and throws RATE_LIMITED (HTTP 429).
    • clientIp finds the caller's address for endpoints used by signed-out visitors.

    In programming terms

    This is a fixed-window limiter stored in Postgres, which avoids running a separate Redis service. The trade-off is that a burst straddling two windows can briefly exceed the average rate. That is acceptable here.

    • The three tests prove: a cursor decodes back to what went in; a cursor with its content swapped but the old signature is rejected; a different secret or garbage text is rejected.
