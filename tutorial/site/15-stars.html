    Part 5 · Stars, safety and admin

    Becoming a Star

    About 3 min read

    Communities exist because Stars exist. A fan applies; an admin reviews (chapter 17); an accepted Star gets the talent role, a profile and their own community. This chapter builds the applicant's and the Star's side.

    Helpers (created in chapter 10)#

    You created server/utils/talent-applications.ts in chapter 10. Here is what its parts are for (the code is on that chapter's page and in the reference):

    • httpsLink: a labelled link that must start with https. Links are only accepted as https so nobody can store a javascript: address that would run code when clicked.
    • rejectMediaIds: file uploads are not built yet, so any attempt to send an uploaded-file ID answers FEATURE_DISABLED with a friendly message. This is a deliberate placeholder.
    • applicationView vs adminApplicationView: the applicant never sees the admin's internalNote or who decided. The admin view adds them. Same data, two audiences.
    • REAPPLY_DAYS = 7: after a decline, reapplyAfter tells the applicant when they may try again.
    • decisionBody: the Zod shape for accept/decline (chapter 17).
    • The claimView functions belong to identity claims, below.

    server/utils/talentProfile.ts, also from chapter 10, holds talentView (a Star's full profile) and talentCard (the short version used by discover).

    Applying#

    server/api/talent-applications/index.post.ts submits an application:

    • A Star cannot apply again; the category must exist and be active; you may have only one pending application; after a decline you must wait out reapplyAfter.
    • The "one pending application" rule is enforced twice: by a check in code (for a friendly message) and by the partial unique index talent_application_one_pending_uq in the schema (so even two simultaneous requests cannot both succeed). The code handles that race by catching the empty returning() result.
    • Rate limited to 5 per hour.

    The Star's own screens#

    Once accepted, a Star has a dashboard with headline numbers and can edit their profile. Both need the talent role.

    In programming terms

    The dashboard runs three counting queries at the same time with Promise.all instead of one after another, which makes the endpoint about as fast as its slowest query rather than the sum. The destructuring [[nm], [pend], [wp]] unpacks "the first row of each result".

    • There is no ID in the address: PATCH /api/talent/profile always edits my own profile. A fan cannot edit someone else's by guessing an ID, because the query is where user_id = me.

    Identity claims (scheduled for removal)#

    Heads-up

    An identity claim lets someone say "this existing Star profile is me" and attach evidence links for an admin to verify. The project plan (docs/plan.md, task 3) removes this feature because the design document has no separate claim flow. The code still exists at this snapshot, so it is shown here so the guide matches it. If you are building your own version, you can safely skip these two files and the identity_claim table.

    Checkpoint

    Submit an application as your test user (use the Reality TV category id from chapter 10):

    The first call returns status pending with HTTP 201. Send it again and you get CONFLICT ("You already have a pending application"). Try a link beginning http:// and see it rejected. In chapter 17 you will accept this application as an admin. Commit: git add -A && git commit -m "Star applications, dashboard and profile".
