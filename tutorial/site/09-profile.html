    My account: profile and deletion

    About 3 min read

    Now that people can sign in, they need to see and change their own details. These three endpoints all live under /api/me: "me" means "whoever the session cookie says is calling".

    Read my profile#

    Create server/api/me/index.get.ts:

    In plain words

    One line does the whole job: requireUser finds out who is calling, and toMe shapes the answer. The { verified: false } option lets a person who has not yet confirmed their email still call this, so an app can show "check your inbox".

    In programming terms

    Any endpoint file is just export default defineEventHandler(async (event) => { … }). The value returned from the function becomes the JSON response, so toMe(...) being the last expression is the response.

    Change my username or display name#

    Create server/api/me/index.patch.ts:

    • PATCH means "change some fields". The Zod shape has .strict() (no unknown fields) and a .refine(...) requiring at least one field.
    • The username must match the same rule used at sign-up (USERNAME_RE from chapter 8) and not be reserved.
    • Once every 30 days: if usernameChangedAt is recent the answer is INVALID_STATE with the date when the next change is allowed.
    • Taken usernames: we check first, but two people could still race for the same name at the same instant. So we also catch the database's own uniqueness error (code === '23505') and turn it into the same friendly CONFLICT. Checking and relying on the database's rule is the safe pattern.

    Delete my account (with a grace period)#

    Deleting someone's data is serious, so it is a two-step process: the request marks the account for deletion, and a daily background job (chapter 14) erases it 30 days later. Signing in during those 30 days cancels it (that hook was in auth.ts). Create server/api/me/index.delete.ts:

    • The caller must send their password again, so a stolen session alone cannot delete the account. It is checked with Better Auth's own verifier (ctx.password.verify), never by us.
    • Rate limited to 5 attempts per hour, because this endpoint accepts password guesses.
    • One transaction sets status = 'pending_deletion' and deletes all of the user's sessions (signing them out everywhere). A transaction means either both happen or neither.
    • It clears the cookie and answers 202 Accepted ("we will do it later") with the date the purge will happen.

    Checkpoint

    With your jar.txt from chapter 8 (sign in again if you deleted it):

    Expect: your profile; the profile with the new display name; a VALIDATION_FAILED error (its details point at the unrecognised key); and finally UNAUTHENTICATED because the last call sent no cookie. Do not try the delete call on the account you want to keep. Commit: git add -A && git commit -m "My account endpoints".

    In programming terms

    You have now seen the usual order inside a write endpoint: 1) authenticate, 2) read and validate input, 3) rate limit if abuse is plausible, 4) check business rules, 5) change the database inside a transaction, 6) return a shaped response. Most of the next chapters repeat this order.
