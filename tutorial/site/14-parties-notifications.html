    Part 4 · Features

    Watch parties, notifications and background jobs

    About 4 min read

    This chapter adds events fans can attend together, the bell that tells them things happened, and two jobs a scheduler calls to keep time-based things correct (reminders and account clean-up).

    Watch parties#

    In plain words

    A watch party is an event listing: a title, a start time, a link to wherever people will actually watch (another website), and an "I'm going" button. Clautverse does not host the video; it only organises the gathering and counts who is coming.

    Create server/utils/watchParties.ts:

    • isIanaTimeZone accepts names like Africa/Lagos by asking JavaScript's built-in Intl to try to use the name. Times are stored in UTC; the zone is kept only so apps can show the local time properly.
    • partyCreateBody and partyPatchBody: the Zod shapes. The patch shape is the create fields made .partial() (all optional), so the two cannot drift apart.
    • assertPartyTimes: a new start time must be in the future and an end must come after the start.
    • loadParty: loads a party with its community and host; "staff" means admin, community owner or host.
    • notifyRsvps: one SQL statement that notifies everyone who RSVP'd.

    In programming terms

    The party row is locked (loadParty(..., true)) so two simultaneous RSVPs cannot both read rsvpCount = 5 and both write 6. The count only changes when a row was really inserted or deleted (changed.length), making repeated calls harmless (idempotent). Wherever you see PUT or DELETE on a "me" address in this project, expect this style.

    Spot the duplication

    The two RSVP files repeat about 20 lines. A shared helper would be tidier, but the project keeps them separate. When you are learning, notice it and decide for yourself; "three similar lines are better than a premature abstraction" is a common rule of thumb.

    Notifications#

    Notifications are rows in the notification table: a type such as drop.published and a small JSON data bag. Create server/utils/notifications.ts:

    • SUMMARY turns a machine type into a sentence for the bell. An unknown type falls back to "Update".
    • TARGETS finds the first ID in data (dropId, partyId, …) to build a target telling the app where to jump when tapped.

    Four small endpoints:

    • Every query includes userId = me, so nobody can read or mark anyone else's notifications. Marking someone else's returns NOT_FOUND.
    • coalesce(read_at, now()) in read.post.ts keeps the first read time if you mark it again.

    Background jobs#

    In plain words

    Some things must happen "on their own": reminding people an hour before a party, switching a party from "scheduled" to "live", and finally erasing accounts whose 30-day deletion grace period ended. A scheduler (a cron service, or a timer on your host) calls two special addresses on a timetable.

    Those addresses must not be public, so they require a secret. Create server/utils/cron.ts:

    • The caller sends Authorization: Bearer <cronSecret>.
    • Any mismatch, including no secret configured at all, answers 404, not 403: an outsider cannot even tell the job exists.
    • The comparison uses timingSafeEqual (the same technique as the cursor) after checking lengths match.

    In programming terms

    Both jobs are written to be idempotent: running one twice does no harm. The reminder query marks reminder_sent_at in the same statement that inserts notifications (a "CTE", the with due as (…) part), so a party is never reminded twice. The purge job deletes at most 100 accounts per run; foreign keys set author columns to null, so posts and the XP ledger survive without a person attached.
