    Part 1 · Set up

    Packages, settings and secrets

    About 8 min read

    The starter is empty. Now we add the libraries Clautverse uses and set up the configuration files. Nothing visible changes yet; this is the groundwork.

    On Windows: step by step#

    Everything on this page works on Windows. A few commands need a different spelling, and this section covers all of them. If you would rather skip the differences, use Git Bash (installed with Git for Windows) or WSL (Ubuntu inside Windows). Both run the guide's commands exactly as written. The steps below use PowerShell, which is already on your computer.

    1. Open PowerShell. Press the Windows key, type PowerShell, press Enter.
    2. Check the tools from chapter 1. Run node -v (it must print 24 or higher), git --version and pnpm -v. Anything missing can be installed from PowerShell with the Windows package manager: Close and reopen PowerShell after installing so it sees the new programs.
    3. Allow pnpm to run. If PowerShell says running scripts is disabled on this system when you type pnpm, run this once, then reopen PowerShell:
    4. Work in a short, plain folder. Keep the project somewhere like C:\dev\clautverse. Avoid folders synced by OneDrive or very long paths; syncing and long paths are common sources of odd install errors on Windows.
    5. Install the libraries. Inside the project folder, run the two pnpm add commands from the next section exactly as shown. They are single lines, so they work in PowerShell unchanged.
    6. Check that it worked. You should see every package from the table below with a version number. Then run pnpm dev and open http://localhost:3000.

    In plain words

    None of the project's packages should need a C++ compiler. If pnpm ever prints a failed "build" step for a package, copy the first error line and look it up; the most common cause on Windows is a project folder inside OneDrive or a path that is too long.

    In programming terms

    winget is Windows' built-in package manager (Windows 10 and 11). pnpm-workspace.yaml (later on this page) tells pnpm which packages may run install scripts; that file is the same on every system.

    Windows differences used later in the guide

    • Random secrets: openssl is not installed on Windows. Use Node instead (the "Secrets" section below shows it).
    • Loading .env: set -a; . ./.env; set +a (chapter 5) is bash only. The "Secrets" section gives the PowerShell version.
    • curl: in Windows PowerShell, curl is a different tool. Type curl.exe, and note that the long curl examples with 'single quoted JSON' are far easier in Git Bash or WSL. The API Explorer page (chapter 19) is a friendlier way to send those requests.
    • Database commands: see PostgreSQL without Docker if you do not want to use Docker Desktop (which needs WSL 2 on Windows).

    Install the libraries#

    In plain words

    A package is code someone else wrote and shared. Instead of writing our own login system or database layer we install tested ones. pnpm add downloads a package and records it in package.json.

    Run these two commands inside the clautverse folder. The versions are the ones this guide was written with. Using the same ones avoids surprises.

    In programming terms

    dependencies are needed when the app runs; devDependencies only while building and testing. postgres is pinned to an exact version (no ^); the others allow compatible updates.

    Add the scripts#

    Open package.json. The starter already has dev, build, generate, preview and postinstall. Add the rest so the scripts section matches this, and add the engines block at the bottom:

    • typecheck: ask TypeScript to find mistakes without running anything.
    • db:generate, db:migrate, db:seed: the three database commands you will use in chapter 5.
    • test, test:unit, test:e2e: run all tests, only the fast ones, or only the full-app ones (chapter 20).

    In programming terms

    "type": "module" in package.json makes every .js file use modern import syntax. The postinstall script runs nuxt prepare after every install to generate the hidden .nuxt type files.

    Tell pnpm which install scripts it may run#

    Create pnpm-workspace.yaml in the project root:

    In plain words

    Some packages run a small setup program when installed. That is a security risk if you do not trust the package, so pnpm blocks them until you say yes. This file says yes to esbuild (a tool Nuxt needs) and no to better-sqlite3. The last line is an empty exception list for another pnpm safety setting, which delays brand-new package releases. If pnpm ever asks you which build scripts to allow, allow esbuild.

    Nuxt settings#

    Replace nuxt.config.ts with this starter version. It adds a block of settings called runtimeConfig. (The finished file has three more lines that we add in chapters 6 and 19, once the files they point to exist.)

    In plain words

    runtimeConfig is a list of settings the server may read. Empty ones ('') are placeholders for secrets that must be provided from outside, so they never appear in the code.

    In programming terms

    Nuxt fills each key from an environment variable named NUXT_ plus the key in UPPER_SNAKE_CASE. So databaseUrl is set by NUXT_DATABASE_URL and betterAuthSecret by NUXT_BETTER_AUTH_SECRET. In server code you read them with useRuntimeConfig(). Keys not under public never reach the browser.

    SettingEnvironment variableWhat it does
    databaseUrlNUXT_DATABASE_URLAddress and login for PostgreSQL
    betterAuthSecretNUXT_BETTER_AUTH_SECRETA long random string the auth library uses to protect its data
    betterAuthUrlNUXT_BETTER_AUTH_URLThe public address of this app (default http://localhost:3000)
    mailtrapApiToken, mailtrapInboxIdNUXT_MAILTRAP_API_TOKEN, NUXT_MAILTRAP_INBOX_IDOptional. If the token is empty, emails are printed in the terminal instead of sent
    emailFromNUXT_EMAIL_FROMThe "from" name and address on emails
    cursorSecretNUXT_CURSOR_SECRETSigns the "next page" tokens so nobody can forge them (chapter 7)
    appVersionNUXT_APP_VERSIONShown by the health check
    authRateLimitEnabledNUXT_AUTH_RATE_LIMIT_ENABLEDSwitch for the login rate limit; the tests turn it off
    cronSecretNUXT_CRON_SECRETPassword for the internal background-job routes (chapter 14)
