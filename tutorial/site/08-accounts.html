    Part 3 · People

    Accounts, sign-in and sessions

    About 6 min read

    Almost everything interesting in Clautverse needs to know who is asking. This chapter adds sign-up, sign-in, email verification and a one-line guard, requireUser, that private endpoints call first.

    The ideas#

    In plain words

    Authentication answers "who are you?" (you sign in). Authorization answers "are you allowed to do this?" (a fan may join a community; only the Star may post in it). After you sign in, the server gives your browser a session cookie, like a festival wristband. On later requests the browser shows it automatically, so you do not log in again for every click.

    In programming terms

    Passwords are never stored; Better Auth stores a salted hash in account.password. The session token lives in the session table and is sent back as a cookie (better-auth.session_token). We do not write any of the cryptography ourselves, which is the right call for security-sensitive code.

    Security

    Authentication code is where mistakes hurt most. Read this chapter to understand it, but before putting real users on any system like this, have someone experienced review it.

    Small helpers first: age and email#

    Clautverse is 18+. Create server/utils/age.ts:

    • ageOn(dateOfBirth, today) counts whole years. It subtracts one if this year's birthday has not happened yet. The today parameter has a default (new Date()) so tests can pass a fixed date.
    • isValidIsoDate accepts only real dates in YYYY-MM-DD form. Note how it builds the date and checks it prints back the same: that catches 2001-02-29, which JavaScript would otherwise quietly turn into 1 March.

    In plain words

    While you develop, no real emails are sent: the text is printed in your terminal, including the confirmation link you would normally click in your inbox. If you later add a Mailtrap account, put its token in .env and the same code sends real mail.

    In programming terms

    $fetch is Nitro's built-in HTTP client. In production a missing token throws, so you can never silently send nothing. process.env.NODE_ENV is production only in a real deployment.

    The Better Auth setup#

    Create server/utils/auth.ts. It is the biggest file so far; the walk-through below explains each block.

    Block by block

    • Constants at the top. USERNAME_RE allows 3 to 30 characters of a-z, 0-9 and _. RESERVED_USERNAMES blocks names like admin and support. DELETION_GRACE_DAYS = 30 is the "change your mind" window for account deletion (chapter 9).
    • emailAndPassword: password login is on, an unverified email cannot sign in (requireEmailVerification), passwords are 8 to 128 characters, and resetting a password signs out other devices. sendResetPassword calls our sendEmail.
    • emailVerification: a confirmation email is sent at sign-up, and clicking the link signs the person in.
    • user.additionalFields: tells Better Auth about our extra columns. input: true means a sign-up request may supply it; input: false means only the server may set it, so nobody can sign up with roles: "super_admin". returned: false hides a field from responses (date of birth stays private).
    • rateLimit: Better Auth's own limiter, stored in the rate_limit table, 30 calls per 60 seconds, switchable with the authRateLimitEnabled setting.
    • databaseHooks.user.create.before: runs just before a new user row is saved. It lower-cases and checks the username, checks the date format, enforces the minimum age (UNDER_MINIMUM_AGE), checks the username is not taken, and forces safe defaults (roles: 'fan', status: 'active') no matter what the caller sent. The comment explains a real bug the project hit: querying through a second database connection while Better Auth holds a transaction can freeze the connection pool when many sign-ups arrive together, so the hook uses Better Auth's current transaction (getCurrentAdapter).
    • databaseHooks.session.create.before: runs before every sign-in. A suspended user is refused (ACCOUNT_SUSPENDED). A user whose deletion is pending can sign in only within the 30-day window, and doing so cancels the deletion.
    • useAuth(): creates the Better Auth object once and reuses it (the same lazy pattern as useDb).

    In programming terms

    The last third of the file is our own guard layer:

    • requireUser(event, { verified, onboarded }) reads the session from the request headers, loads our user row, and throws the right error: UNAUTHENTICATED (no session, or deletion pending), ACCOUNT_SUSPENDED, EMAIL_NOT_VERIFIED, or ONBOARDING_REQUIRED. By default it requires a verified email; endpoints opt into stricter or looser checks. On success it returns the user, which is how handlers get u.id.
    • userRoles splits the comma-separated roles text; toMe shapes the user for the API and deliberately leaves out the date of birth.

    In programming terms

    Errors thrown inside Better Auth's own routes (such as the under-18 rejection) use Better Auth's format, { "code", "message" }, not our { "error": {…} } envelope. Errors from our own endpoints use the envelope. The project's tests rely on this difference.

    jar.txt holds a live session cookie and is not part of the project. Delete it (rm jar.txt) before you commit: git add -A && git commit -m "Accounts with Better Auth".
