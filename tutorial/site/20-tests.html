    Part 6 · Explorer and tests

    Automated tests

    About 4 min read

    You have been checking the app with curl and by clicking. Tests do the same thing automatically, in seconds, every time, and tell you the moment a change breaks a rule. This chapter explains the two kinds in this project and how to run them.

    Why tests matter here#

    In plain words

    Clautverse has rules that are easy to break by accident: "an Originals number is never reused", "a second removal is permanent", "a suspended user cannot sign in". A test is a written promise that a rule still holds. When a promise fails, you find out immediately, not from an angry user.

    • Unit tests check one small function in isolation (ageOn, encodeCursor). They are instant and need nothing else running. You wrote two in chapters 7 and 8.
    • End-to-end (e2e) tests start the real Nuxt app, talk to it over HTTP like a client would, and look at the real database. They are slower but prove the whole chain works.

    The test runner settings#

    You created vitest.config.ts in chapter 7. Look at it again:

    • projects defines the two groups, unit and e2e, so pnpm test:unit and pnpm test:e2e can run them separately.
    • fileParallelism: false makes e2e test files run one after another, because they share one database.
    • Long timeouts for the e2e group allow for creating and migrating a database before the tests start (hookTimeout).

    A fresh database for every run#

    Create tests/e2e/global-setup.ts. It runs once before any e2e test:

    • It drops and recreates a database called clautverse_test, so every run starts clean and your real development data is never touched.
    • It runs the same migrations (drizzle-kit migrate) and the same seed you ran by hand in chapter 5.

    Watch out

    Docker and the clautverse-pg container from chapter 4 must be running. Tests connect to localhost:5432 with the postgres user.

    Helpers shared by every e2e file#

    Create tests/e2e/helpers.ts:

    • testEnv: the settings given to the test copy of the app (database, secrets, and the login rate limit switched off so tests are not throttled).
    • newUser(): makes a unique, valid sign-up body each time.
    • verifiedSession(): signs up, flips email_verified directly in the database (so no email is needed), signs in and returns the cookie. You did the same by hand in chapter 8.
    • api(path, options): a small wrapper around HTTP calls that returns { status, headers, body }.
    • catalog(): looks up the seeded Reality TV and Music categories and the star Ada, which many tests need.

    In programming terms

    setup({ server: true, … }) from @nuxt/test-utils/e2e builds and starts the app on a free port; the helpers' fetch and url then target it. This is why @nuxt/test-utils was installed in chapter 2.

    Reading a real test file#

    tests/e2e/api.test.ts checks the basics from chapters 3 to 10: health, the error shape, sign-up rules, /api/me, account deletion, and onboarding:

    • describe('name', () => { … }) groups tests; it('does something', async () => { … }) is one test.
    • The first lines call await setup(…) to start the app, and afterAll(() => sql.end()) closes the test database connection when finished.
    • Each test follows arrange, act, assert: create a user (arrange), call an endpoint (act), expect(…) something about the answer (assert).
    • Look for the test "unknown routes use the error envelope": it proves the catch-all file from chapter 6 works, and that error.requestId matches the response header.

    The other end-to-end files cover one feature each. Their code is in the reference pages, ready to copy:

    Run them#

    Checkpoint

    pnpm test:unit passes in a second or two. pnpm test:e2e takes noticeably longer (it creates a database and starts the app); every test should pass. When this guide was prepared, Docker was not available on the machine that built the guide, so the end-to-end run was not repeated there. The project's plan file recorded 71 passing e2e tests at an earlier commit; your run shows the current number. Commit: git add -A && git commit -m "Automated tests".

    In programming terms

    A good habit from here on: when you fix a bug, first write a test that fails because of it, then fix it. The sign-up concurrency test above came from exactly that.
