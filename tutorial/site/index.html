    A step-by-step guide

    Build Clautverse from scratch

    Start with an empty Nuxt 4 project. Finish with a working fan-community backend (accounts, communities, posts, missions, moderation) and a live page where you can try every API route.

    No experience needed

    Every idea is explained in plain words first, then in programming terms. If you can type and follow steps, you can follow this.

    Real code only

    Every code box is copied from the real project when this site is built. Nothing is simplified behind your back.

    Checkpoints

    Each chapter ends with something you can run and see, so you always know you are on track.

    What you will have at the end

    • An API (a set of web addresses a phone app or website can talk to) with 24 chapters · 100 API routes, built into one Nuxt 4 project.
    • A database in PostgreSQL with 30 tables, managed with migrations so changes are tracked.
    • Sign-up and sign-in with email verification, using Better Auth.
    • Fan features: pick favourite Stars, join a Star's community, read and react to posts ("drops"), complete missions for XP, RSVP to watch parties, get notifications.
    • Star and admin features: apply to become a Star, review applications, hide a community, handle reports, keep an audit trail.
    • The API Explorer: one web page (built with Vue) that lists every route and lets you send real requests.
    • Automated tests that prove the rules work.

    How to read this guide

    Go in order. Each chapter builds on the one before. Two kinds of side notes appear throughout:

    In plain words

    Everyday language and comparisons. Read these first if a term is new.

    In programming terms

    The same idea, named the way developers name it. This is what you will see in job descriptions and documentation.

    The switch at the top of every page (Both / Plain / Technical) hides one kind if you want a calmer page. Use the search box to find any word. Tick "I finished this chapter" at the bottom of a page to keep your place (it is saved only in your browser).

    What you need before starting

    • A computer (Mac, Windows or Linux) and about 6 to 10 hours spread over a few sittings.
    • A code editor. Visual Studio Code is a good free one.
    • Willingness to type commands in a terminal. Chapter 1 shows exactly what to type.
    • Docker Desktop (a program that runs a database on your computer without a complicated install), or a PostgreSQL 17 you install yourself (see the appendix).

    Honest notes about this guide

    Snapshot

    This guide describes the project at commit e32c941. The project keeps changing (its docs/plan.md lists upcoming tasks such as removing identity claims and adding XP tiers). When code changes, rebuild the guide with node tutorial/build.mjs and the code boxes update by themselves, but the explanations are written by hand and may need an edit.

    Size of the project

    The project has about 100 route files. You will type the foundation and the important routes with full explanations. For the repetitive ones, each feature chapter lists them, shows the code, and the reference pages hold every file in one place to copy from.

    What is not covered

    File uploads (images and voice posts) are not built yet in the project; the routes answer "feature disabled". Deploying to a live server is also outside this guide.

    The chapters

    Start here

    1. The big pictureWhat Clautverse is, the words you need, and how one request travels through the app.

    Part 1 · Set up

    1. Install tools and create the projectInstall Node, pnpm and Docker, then scaffold a plain Nuxt 4 project.
    2. Packages, settings and secretsAdd the libraries, tell Nuxt about our settings, and keep passwords out of the code.
    3. Your first endpointLearn how a file in server/api becomes a web address, and what "auto-import" means.

    Part 2 · Foundations

    1. Run PostgreSQL and design the tablesStart a database in Docker, then describe every table in TypeScript with Drizzle.
    2. Connect, migrate, seed and check healthTurn the table descriptions into real tables, add starter data, and build the health endpoint.
    3. One shape for every errorRequest IDs, a single error format, and a catch-all so the API never answers with a web page by accident.
    4. Checking input, paging and rate limitsReject bad data early, serve long lists page by page with tamper-proof cursors, and slow down abusers.

    Part 3 · People

    1. Accounts, sign-in and sessionsAdd Better Auth with email verification, a username, an age gate, and the guard every private endpoint calls.
    2. My account: profile and deletionRead and edit your own profile, and schedule account deletion with a 30-day safety net.
    3. Categories, Stars and onboardingThe public catalog, and the step-by-step picks a new fan makes before joining communities.

    Part 4 · Features

    1. Communities, joining and OriginalsThe core of the product, with the rules that need transactions and row locks to stay correct.
    2. Drops, replies, likes and the feedPosts by Stars, who can see them, scheduling, replies, and the safe-to-retry trick called idempotency.
    3. Missions, XP and badgesTasks that earn points, a points ledger that can never be silently edited, and collectable badges.
    4. Watch parties, notifications and background jobsScheduled events with RSVPs, an in-app notification inbox, and two protected jobs that run on a timer.

    Part 5 · Stars, safety and admin

    1. Becoming a StarHow a fan applies to be a Star, what a Star sees on their dashboard, and the (soon to be removed) identity claims.
    2. Reports and blocksHow fans flag bad content and hide other people, and the removal rules that protect communities.
    3. The admin area and the audit trailReviewing applications, hiding communities, working the report queue, correcting XP, and logging every step.

    Part 6 · Explorer and tests

    1. The API contract (OpenAPI)A written description of every route that tools, and our Explorer page, can read.
    2. The API Explorer page (Vue)The only web page in the project: it lists every route and lets you send real requests as yourself.
    3. Automated testsUnit tests for small functions, and end-to-end tests that start the whole app against a throwaway database.

    Finish

    1. Check everything and what comes nextA final checklist, how to type-check, common problems, and the project's own roadmap.
