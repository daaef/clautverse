A drop is a post by a Star in their community. This chapter covers creating and scheduling drops, deciding who may read them, replies and likes, and the feed a fan sees.

The rules in plain words

  • Only the community's Star (or an admin) can post. Today only text drops work; voice and image answer "feature disabled" until uploads exist.
  • A drop has an audience: public (anyone), members (the default: people who joined) or originals_only (only members with an Originals number).
  • A drop is a draft until published. It can be published now, or scheduled for later. It becomes visible when its publishAt time passes. No background job is needed: the query simply asks for "published or scheduled and publish time is in the past".
  • Someone who may not read a drop still sees a locked card: who posted, the type, the time and a short teaser, but never the body.
  • Fans can like a drop once and reply to it (one level of nesting).

isLive, liveFilter"Is this drop visible yet?" as a JavaScript check and as a SQL condition.

Idempotency: making "send twice" safe

On a bad phone connection an app may send "create post" and never hear the answer, so it sends again. Without protection the Star ends up with two identical posts. The fix: the app attaches a unique label (an Idempotency-Key) to the request. If the server sees the same label again, it returns the original result instead of creating a second one.

The idempotency_key table stores (userId, scope, key) → resourceId. On create we first call findIdempotent; if there is a hit we return that resource. Otherwise we create the resource and saveIdempotent inside the same transaction, so the key and the resource are saved together or not at all. The header is optional.

Creating, reading, editing, publishing, deleting

server/api/drops/index.post.ts creates a drop:

  • Order inside: authenticate, read the key, validate the body, replay check, rate limit (30 per minute), business rules (text only, body required, publishAt must be in the future, not both publishAt and publishNow), permission (owner or admin), then the transaction.
  • Status comes out as published (publishNow), scheduled (a future publishAt) or draft. Only a published drop triggers member notifications.

docker exec clautverse-pg psql -U postgres -d clautverse -c "update \"user\" set roles = 'fan,super_admin' where email = 'ada@example.com'" curl -b jar.txt -X POST http://localhost:3000/api/drops \ -H 'Content-Type: application/json' -H 'Idempotency-Key: demo-1' \ -d '{"communityId":"COMMUNITY_ID","type":"text","body":"Hello fandom!","publishNow":true}'

Send the exact same command again: you get the same drop id back, not a second drop. That is idempotency at work.
