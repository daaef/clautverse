Time to make the server answer something. You will write a tiny throwaway endpoint, call it, and learn the three rules that explain all ~100 real endpoints in this project.

A throwaway endpoint

Create the folder server/api and inside it a file called hello.get.ts:

export default defineEventHandler(() => { return { message: 'Hello from Clautverse' } })

With pnpm dev running, open a second terminal and ask for it:

curl http://localhost:3000/api/hello

You should get {"message":"Hello from Clautverse"} back. You can also paste http://localhost:3000/api/hello into your browser's address bar. You just built an API endpoint.

curl is a command-line "mini browser". It sends a request and prints the answer. We use it so you can see exactly what the server says, without any page design in the way.

Rule 1: the file name is the address

Nuxt's server engine is called Nitro. It looks at every file under server/api and turns its path into a web address, with no routing code to write. The .get part of the file name says which HTTP method it answers.

File (in server/api)Answers
health.get.tsGET /api/health
communities/index.get.tsGET /api/communities (index means "the folder itself")
communities/[id]/join.post.tsPOST /api/communities/anything/join. [id] is a parameter: whatever is in that spot becomes id.
drops/[id]/reactions/me.put.tsPUT /api/drops/anything/reactions/me
[...].tsAny /api/... address nothing else matched (a "catch-all"). We use it in chapter 6 for tidy "not found" answers.
auth/[...all].tsEverything under /api/auth/; handed to the login library (chapter 8)

This is file-based routing. Several files can share a folder with different methods: index.get.ts and index.post.ts in the same folder are two endpoints on one path. A parameter is read inside the handler with getRouterParam(event, 'id') (the project wraps this in a helper in chapter 7).

Try a parameter. Create server/api/echo/[word].get.ts:

export default defineEventHandler((event) => { return { youSaid: getRouterParam(event, 'word') } }) curl http://localhost:3000/api/echo/banana

The answer is {"youSaid":"banana"}.

Rule 2: return an object and it becomes JSON

A handler is a function. Whatever it returns is sent back; objects and arrays are turned into JSON automatically. To change the status number you call setResponseStatus(event, 201), and to refuse a request you throw an error. You will see all three in the real files.

A handler is like a shop assistant: the request arrives (event is the customer's order slip), the assistant does the work, and hands back an answer.

Rule 3: some functions you never have to import

Notice that defineEventHandler and getRouterParam were used without any import line. Nitro auto-imports its built-in helpers. It does the same for every function we export from files in server/utils. That is why the real endpoints you will read later call requireUser, useDb or readJsonBody without importing them.

Auto-imports are a build-time feature: Nitro scans server/utils and generates the imports for you. The trade-off is that you cannot "click through" from an import line, so this guide always says which file a helper lives in. It also means two utils must not export the same name.

Clean up

These two files were only for learning. Delete them so they do not clutter the project:

rm server/api/hello.get.ts rm -r server/api/echo

curl http://localhost:3000/api/hello no longer returns the greeting (the server now answers "not found"). That is expected, and there is nothing to commit from this chapter.
