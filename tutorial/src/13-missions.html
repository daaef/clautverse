Missions give fans something to do. A Star posts a task, fans complete it, and points (XP) are awarded. The interesting engineering is in how points are stored: as a ledger, never as a number that gets overwritten.

The rules in plain words

  • A mission belongs to one community and is created by its Star (or an admin). It has a title, an XP reward, an optional deadline, and a completion policy: review is auto (instant) or owner (the Star approves), and proof is none, link or text.
  • The XP reward must be inside a range set by admins (default 5 to 100; stored in the app_setting table).
  • Each fan can complete a mission once, and only if they joined the community.
  • Auto missions pay out immediately. Owner-reviewed missions wait as submitted until approved or rejected with a reason.

Think of XP like a bank statement rather than a balance on a sticker. Each earning or correction is a new line. The balance is the sum of the lines. Nobody can quietly change last week's line, so there is always a trail.

The missions helper file

Create server/utils/missions.ts:

  • grantXp is the only way XP changes. It inserts a ledger row. The table has a unique rule on (userId, sourceType, sourceId), so granting for the same completion twice hits onConflictDoNothing and returns the original row instead of paying twice.
  • getXpRules reads the admin-configured range and falls back to DEFAULT_XP_RULES.
  • isExpired / missionStatus: expiry is computed from the deadline, not stored, so nothing has to run at midnight to flip it.
  • loadMission: pending and rejected missions are visible only to staff and the creator.
  • loadCompletionForReview: locks the completion row and insists the caller is staff of that mission's community.
  • badgePatch and badgeBody: Zod shapes for admin badge endpoints (chapter 17). z.url({ protocol: /^https$/ }) accepts only https links.

Completing a mission

server/api/missions/[id]/completions/index.post.ts is where a fan submits:

Everything happens in one transaction: check the mission is open, check the fan is an active member, return the existing completion if there is one, check the proof, insert the completion, and, for auto-review, grantXp then link the ledger row back with xpTransactionId. If any step throws, the whole thing rolls back, so you can never get a completion without its XP or XP without its completion.

The Star (or admin) approves or rejects. Approve grants XP once and notifies the fan; reject needs a reason and grants nothing:

  • Repeating an approve returns the same result (safe to retry). Rejecting an already-approved completion is refused (INVALID_STATE): corrections are made with an admin XP adjustment instead (chapter 17), never by editing history.

Badges

Admins create and award badges (chapter 17). Fans can read the public catalog and their own collection:

As the admin user from chapter 12, create an auto-approved mission, complete it, and look at your XP (use your real community id):

curl -b jar.txt -X POST http://localhost:3000/api/missions \ -H 'Content-Type: application/json' \ -d '{"communityId":"COMMUNITY_ID","title":"Say hi","xpReward":10,"completionPolicy":{"review":"auto","proof":"none"}}' curl -b jar.txt -X POST http://localhost:3000/api/missions/MISSION_ID/completions \ -H 'Content-Type: application/json' -d '{}' curl -b jar.txt http://localhost:3000/api/xp/me

Expected: the completion has status approved, and /api/xp/me shows "balance":10. Send the completion call again: you get the same completion back and the balance stays 10. Try "xpReward":5000 to see the range check fail. Commit: git add -A && git commit -m "Missions, XP ledger and badges".
