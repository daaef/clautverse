Any community product needs a way to deal with bad behaviour. Fans can report something to the admins, or block a person so they stop seeing that person's content. This chapter builds both, plus the helper admins use to remove a member.

Reports

A report is a flag on a drop, reply, user, community or mission with a reason (spam, harassment, hate, sexual, impersonation, other). It joins a queue that admins work through in chapter 17. The person reported is never told who reported them.

Create server/utils/reports.ts:

  • isUniqueViolation recognises the database's "that already exists" error code (23505), even when wrapped inside another error.
  • assertReportTarget: you may only report something you are able to see. It reuses loadDrop, loadVisibleCommunity and loadMission, so a hidden or non-existent target simply answers NOT_FOUND.
  • reportSubject: for admins, finds the author and community behind whatever was reported.
  • removeMember: the removal rule. A member removed from a community has their Originals number retired (the row keeps it; the counter never hands it out again). The first removal blocks rejoining for 30 days; a second removal is permanent. The member is notified, the action is audited, and the member count goes down, all inside the caller's transaction.

server/api/reports/index.post.ts:

  • One open report per reporter and target. A repeat returns the existing report instead of creating spam. The check runs before the rate limit, so repeating is free.
  • The reported item must be visible to the reporter.
  • If two identical reports race, the database's unique index rejects the second; the catch block then loads and returns the first. Handling the race this way is common: let the database be the final judge, and turn its error into a normal answer.

Blocks

A block is private and one-directional: if I block you, I stop seeing your drops and replies. You are not told, and nothing else changes for you. It is about what I see.

server/api/users/[id]/block.post.ts and block.delete.ts:

  • You cannot block yourself (VALIDATION_FAILED), and the target must exist.
  • Blocking twice returns the existing block; unblocking something that is not blocked still succeeds. Both are idempotent, so apps can retry freely.
  • The blocking itself is only a row. The effect happens elsewhere: the feed, community timeline, single-drop and reply endpoints from chapter 12 all call blockedAuthorIds and notAuthoredByBlocked. That is why those helpers live in drops.ts.
  • This is the first place user IDs are used as a path parameter, so it uses readUserIdParam from chapter 7 (Better Auth IDs are not UUIDs).

As your test user, report the drop from chapter 12, repeat the report, and try to block yourself (use your own user id from /api/me):

curl -b jar.txt -X POST http://localhost:3000/api/reports \ -H 'Content-Type: application/json' \ -d '{"targetType":"drop","targetId":"DROP_ID","reason":"spam"}' curl -b jar.txt -X POST http://localhost:3000/api/reports \ -H 'Content-Type: application/json' \ -d '{"targetType":"drop","targetId":"DROP_ID","reason":"spam"}' curl -b jar.txt -X POST http://localhost:3000/api/users/YOUR_USER_ID/block

Expected: the first call returns status open with HTTP 201; the second returns the same report with HTTP 200; the block call returns VALIDATION_FAILED with fields.id = "self". Commit: git add -A && git commit -m "Reports and blocks".
