The starter is empty. Now we add the libraries Clautverse uses and set up the configuration files. Nothing visible changes yet; this is the groundwork.

Install the libraries

A package is code someone else wrote and shared. Instead of writing our own login system or database layer we install tested ones. pnpm add downloads a package and records it in package.json.

Run these two commands inside the clautverse folder. The versions are the ones this guide was written with. Using the same ones avoids surprises.

pnpm add better-auth@ drizzle-orm@ postgres@ yaml@ zod@ pnpm add -D drizzle-kit@ @nuxt/test-utils@ @types/node@ typescript@ vitest@ vue-tsc@

Add the scripts

Open package.json. The starter already has dev, build, generate, preview and postinstall. Add the rest so the scripts section matches this, and add the engines block at the bottom:

  • typecheck: ask TypeScript to find mistakes without running anything.
  • db:generate, db:migrate, db:seed: the three database commands you will use in chapter 5.
  • test, test:unit, test:e2e: run all tests, only the fast ones, or only the full-app ones (chapter 20).

In programming terms

"type": "module" in package.json makes every .js file use modern import syntax. The postinstall script runs nuxt prepare after every install to generate the hidden .nuxt type files.

Nuxt settings

Replace nuxt.config.ts with this starter version. It adds a block of settings called runtimeConfig. (The finished file has three more lines that we add in chapters 6 and 19, once the files they point to exist.)

// https://nuxt.com/docs/api/configuration/nuxt-config export default defineNuxtConfig({ compatibilityDate: '2025-07-15', devtools: { enabled: true }, runtimeConfig: { databaseUrl: '', betterAuthSecret: '', betterAuthUrl: 'http://localhost:3000', mailtrapApiToken: '', mailtrapInboxId: '', emailFrom: 'Clautverse ', cursorSecret: '', appVersion: 'dev', authRateLimitEnabled: true, cronSecret: '', }, })

runtimeConfig is a list of settings the server may read. Empty ones ('') are placeholders for secrets that must be provided from outside, so they never appear in the code.

Nuxt fills each key from an environment variable named NUXT_ plus the key in UPPER_SNAKE_CASE. So databaseUrl is set by NUXT_DATABASE_URL and betterAuthSecret by NUXT_BETTER_AUTH_SECRET. In server code you read them with useRuntimeConfig(). Keys not under public never reach the browser.

mailtrapApiToken, mailtrapInboxIdNUXT_MAILTRAP_API_TOKEN, NUXT_MAILTRAP_INBOX_IDOptional. If the token is empty, emails are printed in the terminal instead of sent

Secrets: the .env file

Create .env.example (a template that is safe to save in git) with these contents:

Now make your real, private copy and fill in the two secrets:

cp .env.example .env openssl rand -base64 32 openssl rand -base64 32

Each openssl line prints a random string. Paste one after NUXT_BETTER_AUTH_SECRET= and the other after NUXT_CURSOR_SECRET=. For NUXT_CRON_SECRET you can paste a third. On Windows without openssl, any long random string works (a password manager can make one).

Never save .env in git. It holds secrets. The next file prevents that. If you ever commit a real secret by accident, treat it as leaked and replace it.
