Now the app meets the database. You will write the connection helper, create the real tables, add a few starter rows, and build the first real endpoint: a health check.

The connection helper

Create the folder server/utils and the file server/utils/db.ts:

Opening a connection is slow, so we open it once, the first time anyone needs it, and then reuse it. useDb() is the door every endpoint walks through to reach the database.
  • let _db at the top is a lazy singleton: created on first call, reused afterwards.
  • useRuntimeConfig().databaseUrl reads the setting from chapter 2. No URL means a clear error instead of a confusing one later.
  • prepare: false turns off prepared statements. The comment explains why: it keeps us compatible with Neon's pooled (PgBouncer) database endpoint, a hosted Postgres we may use later.
  • max: 5 allows at most five connections at once.
  • export { schema } makes the table definitions available everywhere. Because Nitro auto-imports exports from server/utils, any endpoint can write useDb() and schema.community with no import.

Create the real tables (migrations)

A migration is a dated instruction like "add this drawer to the filing cabinet". Instead of editing the database by hand, we generate instructions from our TypeScript and run them in order. Anyone who runs the same instructions ends up with the same cabinet, and every change is saved in git.

First, make your .env values visible to the two Drizzle commands. (Nuxt reads .env by itself when the app runs, but drizzle-kit is a separate tool and does not.) Run this once per terminal window:

set -a; . ./.env; set +a

Then generate and apply the migration:

pnpm db:generate pnpm db:migrate
  • db:generate compares your schema files with the previous state and writes a numbered SQL file into server/db/migrations, such as 0000_something_random.sql, plus a meta folder that remembers the state. The random name part is chosen by the tool.
  • db:migrate runs any migration files the database has not seen yet.

Open the generated .sql file: it is ordinary CREATE TABLE statements, one per table, with the constraints from your TypeScript. The project you are copying has nine migration files because its tables grew over time (for example shows and seasons were added and later removed). Yours will have one, because you are creating the final shape in one go. The result is the same set of tables.

(Local PostgreSQL without Docker? Use the psql "$NUXT_DATABASE_URL" form from the appendix instead of docker exec.)

Look inside the database. This runs a command inside the Docker container and lists the tables:

docker exec clautverse-pg psql -U postgres -d clautverse -c '\dt'

You should see tables. (Drizzle also keeps its own record of which migrations have run, in a separate place that this list does not show.)

After this point, never change a table by editing the database by hand. Edit the schema file, run pnpm db:generate, then pnpm db:migrate. That keeps your project and your database in agreement.

Starter data (the seed)

The tables are empty. Fans pick a category and favourite Stars during onboarding, so we need some to exist. Create scripts/seed.mjs:

  • It inserts three categories (only Reality TV is active), three countries, and three placeholder Stars (Ada, Bisi, Chidi).
  • on conflict (slug) do nothing makes the script idempotent: running it twice does not create duplicates.
  • sql.begin(async (tx) => ...) wraps everything in a transaction, so either all rows go in or none.
pnpm db:seed

The terminal prints seeded.

The health endpoint

A health check is a tiny endpoint that says "I am running, and my database answers". Hosting services and humans ping it. Create server/api/health.get.ts:

  • setResponseHeader(event, 'Cache-Control', 'no-store') tells browsers and proxies not to remember the answer.
  • select 1 is the cheapest possible question to the database. If it answers, the database is alive.
  • On failure the endpoint still replies (so monitors get a clear answer), but with status 503 (service unavailable).

Start the app with pnpm dev, then run curl http://localhost:3000/api/health. Expected, from reading the code: {"status":"ok","db":"ok","version":"dev"}. Now stop the database with docker stop clautverse-pg and call it again: you should get status: "error" with a 503. Start it again with docker start clautverse-pg.
