The guide uses Docker so the database is one command. If you would rather install PostgreSQL directly on your computer (or already have it), this page gives you the replacements. Everything else in the guide stays the same.

Which version

PostgreSQL is the program that stores all the data. Docker was only a convenient box to run it in. You can run the same program directly on your computer instead, and the app will not notice the difference.

The guide uses PostgreSQL 17 (the Docker image is postgres:17, from the project's README). Install 17 if you can. The project's tests drop a database with with (force), which needs PostgreSQL 13 or newer, so any recent version should work, but 17 is the one the guide was written against. Check yours with:

psql --version

1. Install and start it

Installing gives you the database program plus a background "service" that keeps it running, like a shop that stays open while you work.
SystemInstallNotes
macOS (Homebrew)brew install postgresql@17 then brew services start postgresql@17Homebrew does not put psql on your path for versioned installs. Add /opt/homebrew/opt/postgresql@17/bin to your PATH (on Intel Macs the folder starts /usr/local/opt). Your login is a database superuser with no password.
Ubuntu / Debiansudo apt install postgresqlThe version depends on your release; check with psql --version. The service starts automatically. The superuser is the system user postgres, reached with sudo -u postgres psql.
WindowsThe installer from postgresql.org/download/windowsThe installer asks for a password for the postgres user and a port (keep 5432). Use "SQL Shell (psql)" from the Start menu, or add the bin folder to your PATH.

These commands come from each system's usual package route and are not tested by this guide. If one differs on your machine, the PostgreSQL download page for your system is the authority.

2. Create the database and a login

The Docker command created a database called clautverse with the user postgres and the password postgres in one go. Locally you do the same two things by hand.

Open psql as the superuser (macOS: psql postgres; Ubuntu: sudo -u postgres psql; Windows: SQL Shell) and run:

create database clautverse; alter user postgres with password 'postgres';

Still inside psql, type \l. The list of databases should include clautverse.

The second line is optional on macOS Homebrew, where you can use your own login without a password. It is a throwaway local password; never use it anywhere real. Type \q to leave.

3. Point the app at it

In .env, set NUXT_DATABASE_URL to match what you created. The pattern is postgres://user:password@host:port/database:

Your setupNUXT_DATABASE_URL
You ran step 2 exactlypostgres://postgres:postgres@localhost:5432/clautverse (the same as the guide)
macOS Homebrew, your own loginpostgres://YOUR_MAC_USERNAME@localhost:5432/clautverse
A different password or portPut your values in the same pattern

Run set -a; . ./.env; set +a then psql "$NUXT_DATABASE_URL" -c "select 1". A table with a 1 means the address, login and database are right. If you changed .env while pnpm dev was running, restart it.

The app and Drizzle only ever read the address in NUXT_DATABASE_URL; postgres.js (chapter 5) opens a normal TCP connection to it. Docker or a local install is invisible to the code, which is why only the setup commands change.

Everything else (pnpm db:generate, pnpm db:migrate, pnpm db:seed, the health check) is identical, because the app only ever sees the address in NUXT_DATABASE_URL.

5. Tests with a local database

The end-to-end tests (chapter 20) create and delete a separate database called clautverse_test. They connect first to a maintenance address that defaults to postgres://postgres:postgres@localhost:5432/postgres (in tests/e2e/global-setup.ts and tests/e2e/helpers.ts). That default matches the user and password from step 2. If yours differ, or you use the macOS login without a password, set TEST_DATABASE_ADMIN_URL before running them:

export TEST_DATABASE_ADMIN_URL=postgres://YOUR_USER:YOUR_PASSWORD@localhost:5432/postgres pnpm test:e2e
  • The user must be allowed to create and drop databases (a superuser, as in the steps above, is).
  • The test database name is built by replacing the last part of that address with clautverse_test, so keep the /postgres ending.
  • Your real clautverse data is never touched by the tests.

With the local database running, chapters 5 onward work unchanged: pnpm db:migrate, pnpm db:seed, then curl http://localhost:3000/api/health should return {"status":"ok","db":"ok","version":"dev"}. Commit as usual.

Docker or local: which should I use?

  • Docker: one command, identical for everyone, easy to throw away and recreate. Needs Docker Desktop running.
  • Local install: no Docker to run, starts with your computer, and you can use any PostgreSQL tool you already know. You manage the version and login yourself.

The app and the tests behave the same with either.
