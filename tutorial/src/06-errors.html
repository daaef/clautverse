Things go wrong: a missing page, a forbidden action, a bug. A good API reports each of them in one predictable shape so the app using it can react properly. This chapter builds that.

Why a standard error shape

Imagine every shop in a mall using a different kind of receipt. Cashiers would waste time decoding them. We make our server print the same receipt for every problem.

Every error from Clautverse looks like this:

{ "error": { "code": "NOT_FOUND", "message": "Not found.", "requestId": "req_5f2c…", "details": { } } }
  • code: a fixed word a program can check (NOT_FOUND, FORBIDDEN, VALIDATION_FAILED...).
  • message: a sentence for a human.
  • requestId: a label you can quote when asking "what happened to request X?".
  • details: optional extras, such as which input field was wrong.

Step 1: the list of error codes

Create server/utils/api-error.ts:

  • ERROR_STATUS pairs each code with its HTTP status number. 401 UNAUTHENTICATED means "I do not know who you are"; 403 FORBIDDEN means "I know who you are, and no". 409 means the request clashes with the current state.
  • as const freezes the list so TypeScript knows the exact words. ErrorCode = keyof typeof ERROR_STATUS then means "one of these words", so a typo like 'NOTFOUND' is caught while you type.
  • apiError(code, message, details?) builds an error object. You use it as throw apiError('NOT_FOUND', 'Community not found.').

Step 2: stamp every request with an ID

Middleware is code that runs on every request before the endpoint. Create server/middleware/00.request-id.ts:

  • It makes an ID like req_ plus a random UUID, stores it on event.context (a notebook that lives for one request) and also sends it back in an X-Request-Id header.
  • The 00. in the file name controls order: middleware files run alphabetically, so this one runs first.

Step 3: the one error handler

Create server/error-handler.ts. Every error thrown anywhere in the server ends up here:

  • It works out the code: our own apiError already carries one in data.code; for other errors it guesses from the status number (404 becomes NOT_FOUND, 401 UNAUTHENTICATED, and so on).
  • Server bugs never leak. For any 5xx status the code becomes INTERNAL, the message becomes the harmless "Something went wrong.", and the real error goes only to the terminal log, tagged with the request ID.
  • details are included only for 4xx errors.

Security note

Showing a raw error message or stack trace to the outside world can reveal file paths, database names and other secrets. That is why 5xx messages are replaced.

Now tell Nitro to use this file. In nuxt.config.ts add this block after runtimeConfig:

nitro: { errorHandler: '~~/server/error-handler.ts', },

~~ means "the project root" (a single ~ means the app/ folder in Nuxt 4). Restart pnpm dev after changing nuxt.config.ts.

Step 4: a catch-all for unknown addresses

Without this, a typo such as /api/nope would return Nuxt's HTML "page not found". An API should answer in JSON. Create server/api/[...].ts:

With the app running:

curl -i http://localhost:3000/api/nope

You should see status 404, an x-request-id: req_… header, and a JSON body whose error.code is NOT_FOUND and whose error.requestId equals the header. (The project's own test checks exactly this, in chapter 20.) Commit: git add -A && git commit -m "Standard error shape and request IDs".
