Admins keep the platform healthy. Their endpoints all live under /api/admin and share one rule: every action is checked, reasoned and recorded. This chapter shows the pattern with the most important routes and lists the rest.

How admin access works

An admin is a normal account with an extra role word, super_admin, in its roles text. There is deliberately no public way to get that role: sign-up forces roles to fan (chapter 8). You grant it by hand in the database, as you did in the chapter 12 check:

 update "user" set roles = 'fan,super_admin' where email = 'ada@example.com';

Every admin endpoint begins with const admin = await requireAdmin(event) (from admin.ts, chapter 11), which answers UNAUTHENTICATED or FORBIDDEN as appropriate.

The same four-part shape repeats in almost every admin write: 1) requireAdmin; 2) validate the body (a reason is usually required); 3) a transaction that locks the row (.for('update')), checks its current state, changes it; 4) audit(...) and often notify(...) inside that same transaction, so a change can never exist without its audit row.

Accepting a Star's application

This is the endpoint that turns a fan into a Star. You wrote the application side in chapter 15.

Inside one transaction it: locks the application; returns quietly if it is already accepted (safe to retry); refuses if it was declined; creates the talent profile with a unique slug (or reuses one); creates the Star's community with ensureTalentCommunity; adds the talent role with grantRole; marks the application accepted; writes the audit row; and notifies the applicant. If any step fails, none of it happens.

Working the report queue

server/api/admin/reports/[id]/actions.post.ts applies one of five actions to a report and closes it:

  • dismiss, remove_content, suspend_user, remove_member or veto_community.
  • It first looks up what was reported with reportSubject (chapter 16), and rejects an action that makes no sense for that target (for example remove_content on a user report) with not_applicable.
  • suspend_user and remove_member reuse suspendUser and removeMember so the rules are written once.

Hiding a community (veto)

Veto only flips status to vetoed. Memberships and Originals numbers are untouched, so a restore brings everything back. The hiding itself is done by loadVisibleCommunity (chapter 11).

Correcting XP without rewriting history

  • A correction is a new ledger row (positive or negative, never zero) with a required reason and the admin's ID. A random UUID is used as sourceId because each adjustment is its own event.
  • It is also written to the audit log.

The audit log

This is read-only: no route in the project updates or deletes admin_audit rows. Admins can filter by who, what kind of target and a time range.

Suspending a user

The handler is three lines because the logic lives in suspendUser (chapter 11): admins cannot be suspended, and suspending deletes the person's sessions so they are signed out everywhere.

curl -b jar.txt "http://localhost:3000/api/admin/applications?status=pending" curl -b jar.txt -X POST http://localhost:3000/api/admin/applications/APPLICATION_ID/accept \ -H 'Content-Type: application/json' -d '{}' curl -b jar.txt "http://localhost:3000/api/admin/audit" curl -b jar.txt http://localhost:3000/api/communities
