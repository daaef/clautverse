A community is the home of one Star's fans. This is the heart of Clautverse, and it contains the trickiest rule: the first 100 members get permanent "Originals" numbers, even when hundreds of people join at the same instant.

The shared toolbox: admin.ts

Before communities, we add the helper file that many chapters use. Despite its name it holds more than admin code. Create server/utils/admin.ts:

A view function such as publicUser is a deliberate filter between the database row and the outside world. Rows contain private things; views decide what is allowed to leave the building. Almost every …View function in this project exists for that reason.

Community helpers

Create server/utils/community.ts:

  • optionalUser(event): for pages anyone can see, but which look different when signed in. It returns the user or null and never throws.
  • isAdmin, isCommunityOwner: the two "who is staff here?" checks.
  • loadVisibleCommunity(id, viewer, tx, lock): loads a community, or throws NOT_FOUND. A vetoed community (hidden by an admin) looks non-existent to everyone except admins. With lock = true it adds FOR UPDATE, explained below.
  • communityCard, communityDetail, membershipView: the shapes returned to callers. Notice originalPosition is hidden (null) for a removed member.
  • ORIGINALS_CAP = 100: the one place the number lives.

Joining: the hard part

Picture a signing-up desk giving out numbered badges 1 to 100. If two assistants each look at the list, both see "next number: 57", and both hand out 57, you have a problem. The fix is to let only one assistant work at the desk at a time. In the database that is a row lock.

Create server/api/communities/[id]/join.post.ts:

Read it in this order:

  1. Guards. requireUser(event, { onboarded: true }) (finish onboarding first), the ID, a rate limit (60 per hour), and a Zod body. A lane is required, one of six codes.
  2. Open a transaction and lock the community row with loadVisibleCommunity(id, null, tx, true). Anyone else joining the same community waits here until this transaction finishes.
  3. Already an active member? Return the existing membership (status 200). Joining twice is harmless.
  4. Previously removed? The first removal blocks rejoining for 30 days (blockedUntil); a second removal is permanent. Either returns FORBIDDEN.
  5. Previously left? Reactivate the same row with the newly chosen lane. Their Originals number stays retired.
  6. Brand new? If fewer than 100 numbers have been handed out, take the next one (originalsAssigned + 1); otherwise originalPosition is null (a normal member). Insert the membership and bump the counters.
  7. Respond with 201 if a new row was created, 200 otherwise.
  • .for('update') is SQL's SELECT … FOR UPDATE. Because the community row is locked, the "read counter, then write counter + 1" sequence cannot interleave with another join. There is also a database-level safety net: unique(communityId, originalPosition) in the schema.
  • onConflictDoNothing() plus the fallback select handles the duplicate-sign-up race without crashing.
  • originalsAssigned is a counter that only increases. When a member leaves, originalPosition is set to null but the counter does not go down, so numbers are never reused.
  • sql`${c.memberCount} + 1` makes the database do the addition, so two updates cannot overwrite each other with stale numbers.

Leaving, listing members, the Originals wall

server/api/communities/[id]/leave.post.ts:

  • The Star cannot leave their own community (INVALID_STATE).
  • Leaving clears the lane and the Originals number in the same transaction as the status change. The counter memberCount goes down with greatest(x - 1, 0) so it can never go negative.

Communities are normally created when an admin approves a Star (chapter 17). To test now, create one by hand for the seeded Star Ada:

docker exec clautverse-pg psql -U postgres -d clautverse -c "insert into community (owner_talent_id, slug, name) select id, slug, name from talent where slug = 'ada'" curl http://localhost:3000/api/communities

Copy the community id, then join as the onboarded fan from chapter 10:

curl -b jar.txt -X POST http://localhost:3000/api/communities/COMMUNITY_ID/join \ -H 'Content-Type: application/json' -d '{"lane":"rider"}'

Expect status 201 and "originalPosition":1. Repeat the same call: status 200, same membership. Open /api/communities/COMMUNITY_ID/originals to see slot 1. Call /leave, then join again with another lane: originalPosition is now null because number 1 is retired for good. Commit: git add -A && git commit -m "Communities, joining and Originals".
