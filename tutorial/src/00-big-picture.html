Before typing anything, get the map. This chapter has no code to write. It explains what we are building and gives names to the pieces so the later chapters feel familiar.

What Clautverse is

Clautverse is a place for fans of public figures. Think of a reality-TV housemate. Their fans can join a community for that person, read what the person posts, do small missions to earn points, RSVP to watch-together events, and get notified when something happens. Staff (admins) approve who counts as a real "Star", handle reports about bad behaviour, and can hide a community.

We are building the backend: the part that stores everything and enforces the rules. It has no pretty screens. Instead it has an API, which is a list of web addresses that other programs (a phone app, a website) can ask for things. The only web page we build is the API Explorer, a tool for trying those addresses by hand.

The words specific to Clautverse

  • Fan: a normal signed-in user.
  • Star: a public figure. The code calls this a talent (table talent, routes under /api/talents). Same thing, two names.
  • Category: a kind of fandom, such as Reality TV. Only active categories can be chosen.
  • Community (fandom): the home of one Star's fans. One Star owns exactly one community.
  • Originals: the first 100 people to join a community get a permanent numbered spot, 1 to 100. Leave or get removed and your number is retired forever.
  • Lane: one of six labels a fan picks when joining (rider, fandom_builder, builder, analyst, creator, mutual).
  • Drop: a post by the Star. It can be public, members-only, or Originals-only.
  • Mission and XP: a task a Star sets, and the points a fan earns by completing it. XP is recorded in a ledger (a list of every change), never edited.
  • Badge: a collectable award given by admins.
  • Watch party: a scheduled event with an external link and an "I'm going" button.
  • Report and block: how fans flag content and hide other users.

One request, start to finish

This is the journey every call to the API takes. Later chapters build each stop.

  1. The request arrives (for example POST /api/communities/abc/join).
  2. Middleware stamps it with a request ID so we can trace problems (chapter 6).
  3. Nitro finds the file that matches the address (chapter 3).
  4. The handler checks who you are using your session cookie (chapter 8).
  5. It validates the input with Zod and applies rate limits (chapter 7).
  6. It talks to the database, often inside a transaction (chapters 4 and 5).
  7. It returns JSON. If anything went wrong, one error handler turns it into the same error shape every time (chapter 6).
